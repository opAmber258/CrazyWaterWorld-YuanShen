# 模型资产交付约定

> 适用：所有美术资产的记录分工、上下文读取、发布和登记；本文涉及 `.geo.json` 的格式条款与四件套规格针对 **Bedrock 格式**。
> `java_block` 的模型规格继续遵循 `.mex/patterns/blockbench-modeling.md`，交付 Java 模型 JSON，不要求 `.geo.json`；共用记录、验证摘要与发布规则仍按本文执行。
> 登记处：[Discussion #39 · 模型资产统计](https://github.com/opAmber258/CrazyWaterWorld-YuanShen/discussions/39)。
> 运行手册：`.mex/patterns/deliver-model-asset.md`。

本文档是上述范围内资产交付的**唯一权威约定**。其它位置的说明若与本文冲突，以本文为准。

**范围边界**：本文档只约束**交付物的形态**——命名、目录结构、文件规格、登记格式、发布边界。**建模手法、资产尺寸、比例与美术质量由作者自行把控**，本约定不设规范；评审只判定交付是否合规（见第 6 节自查与第 9 节退回条件）。

## 0. 角色与产出边界

| 角色 | 职责 |
| --- | --- |
| 美术作者 | 在 Blockbench 完成 `.bbmodel`，产出几何、贴图、预览与验证记录，按本文组织目录 |
| 集成者 | 把定案资产接入 `src/main/resources` 并在游戏内验证 |
| 维护者 | 在 Discussion #39 评选候选、决定升入正式资产、归档落选版本 |

美术侧交付**不含**游戏代码改动。资产从「待评选」升入「正式」之后，才由集成者做运行时接入。

## 1. 命名

### 1.1 资产名

**中文官方译名 + 官方英文名（驼峰）**，例如：焊接工具 WeldingTool、导航终端 NavigationTerminal、核反应堆 NuclearReactor。

中英两名**必须分别查证**，不能从同一份文件推出来：

| 需要 | 查证来源（均在游戏安装目录，不在本仓库内） |
| --- | --- |
| 中文译名 | `Content/Texts/SimplifiedChinese/SimplifiedChineseVanilla.xml` 的 `<entityname.标识>` |
| 官方英文名 | 英文文本 `Content/Texts/English/EnglishVanilla.xml` 的同标识条目；或实体定义文件（`Content/Items/**/*.xml`）中的显示名 |

- 简中文件的条目值**只有中文**，部分条目只有中文无英文对应，不能据此推断英文名。
- **不得凭印象或从英文直译**。查证结果及两个条目标识只记入 `validation.json.sources`，README 链接引用。
- 英文名取官方英文的驼峰形式（`Nuclear Reactor` → `NuclearReactor`），**不是**文件标识的驼峰（`reactor1` → Reactor）。
- 原版没有对应实体时（自创生物、项目特有构件），使用项目定名，并在讨论条目里**注明"非原版实体，项目定名"**。已知例：噬海女妖 Charybdis、压载泵 BallastPump。

### 1.2 制作来源标注（必填）

每件资产必须标明**制作来源**、**贡献者**；涉及 AI 时还要写明**所用模型**。

| 来源 | 标注格式 | 必填项 |
| --- | --- | --- |
| 人类制作 | `制作来源：人工（<贡献者>）` | 贡献者名称 |
| AI 制作 | `制作来源：AI（<模型名>）` | AI 模型完整名称与所用工具 |
| 人机协作 | `制作来源：人工 + AI（<贡献者> + <模型名>）` | 贡献者名称、AI 模型名、双方分工 |

示例：`制作来源：人工 + AI（TakaraMiyuki + GPT 6.1 Sol）`

**具体要求：**

1. **贡献者与分工只在 `validation.json` 的 `contributors` 中维护一次**；`creation_source` 从贡献者生成。README 首屏链接到该记录；需要展示来源摘要时，从记录生成，不另行手填；
2. **Discussion #39 候选条目**在任务复选框**之后**加 `🤖` 标记（格式 `- [ ] 🤖 候选 A…`），与人工资产区分。**不要写成 `🤖 - [ ] …`** —— 那会让 GitHub 不再把该行识别为可勾选的任务列表项；
3. **发布报告**引用同一提交的验证记录；如需展示 AI 参与范围，从该记录生成摘要；
4. **评审强度不降低** —— AI 产出必须逐项走第 6 节自查，且原作者需确认视觉结论；不得以"AI 生成"为由跳过评审；
5. **`validation.json` 结构化记录**：写入 `contributors` 字段，格式为
   `{"human": ["<贡献者>"], "ai": [{"name": "<模型名>", "tool": "<工具>", "role": "<职责>"}], "division": "<分工说明>"}`，
   同时写入 `creation_source` 一行摘要，以及 `display_name_zh` / `display_name_en`。

贡献者名称使用与 Git/GitHub 提交一致的标识（如 `TakaraMiyuki`），便于溯源；AI 模型写完整版本（如 `GPT 6.1 Sol`、`GLM-5.3-Flash`），不写"某 AI"。

已存在的资产在下次修改时补标，不追溯强制补齐。

> **为何在上游记录 AI 模型名**：不同模型的造型习惯、细节密度与错误模式不同。出现形变、UV 串位或风格漂移时可按模型归类排查，也便于判断哪些环节适合继续交给 AI、哪些需要人工兜底。

### 1.3 标识与路径

| 项 | 规则 | 示例 |
| --- | --- | --- |
| mod 标识 | 小写 + 下划线，与资源文件名一致 | `navigation_terminal` |
| 资产目录 | `art/models/<标识>_<YYYYMMDD>/` | `navigation_terminal_20261108/` |
| 主工程 | `<标识>.bbmodel` | `navigation_terminal.bbmodel` |
| 几何导出 | `<标识>.geo.json` | `navigation_terminal.geo.json` |
| 贴图 | `<标识>_tex.png` | `navigation_terminal_tex.png` |
| 预览 | `preview_{front,back,side,oblique}.png` | `preview_oblique.png` |

同一资产的多件变体（如门的 3x1 / 4x）追加后缀：`bulkhead_door_3x1.bbmodel`。

## 2. 目录与版本

### 2.1 标准结构

```text
art/models/<标识>_<YYYYMMDD>/
├── <标识>.bbmodel
├── <标识>.geo.json
├── <标识>_tex.png
├── preview_front.png / preview_back.png / preview_side.png / preview_oblique.png
├── README.md
├── validation.json
├── structure_audit.json        （按需，详细异常证据）
└── reference/                  （原作裁切、调色板、资产特有参数与必要证据）
```

### 2.2 允许的例外

- **扁平命名**：早期资产直接放在 `art/models/` 根下（`engine.bbmodel`、`reactor.bbmodel`、`ballast_pump.bbmodel`、`small_pump.bbmodel`）。这些属于**历史豁免**，不强制迁移；但**新资产一律使用日期目录**。
- 历史豁免资产在补齐 README 与 validation 之前，只能留在「待评选」，不得升入「正式资产」。

### 2.3 不入库的内容

- `art/models/.work/` —— 过程工作区（截图、脚本、临时导出）。**不提交**。
- `art/models/_archive/` —— 落选版本与历史修订。**不提交**（需要保守留档时，单独走一次提交并说明）。
- `.blockbench_launch.log` 等工具日志。

## 3. 交付物规格

### 3.1 四件套（缺一不可）

| 文件 | 规格 |
| --- | --- |
| `.bbmodel` | Blockbench 5.2.2 可重新打开编辑；贴图内嵌；不依赖本机路径 |
| `.geo.json` | Bedrock Entity 几何，`format_version` 与项目现有资产一致；identifier `geometry.<标识>` |
| `_tex.png` | RGBA 像素图，2 的幂（32/64/128/256/512）；无渐变、无噪点；透明像素真透明 |
| 预览 ×4 | 1200×900；透明或纯色底、无网格、无 UI；正/背/侧用正交，斜视用透视 |

**预览尺寸生效边界**：1200×900 自 2026-11-10 起适用于**新增资产**，以及**因几何改动而重出预览**的存量资产。存量资产在下次重出预览前一并达标，不单独追溯重渲染 —— 与第 1.2 节（制作来源标注）、第 10 节（历史资产整改）同一原则。

### 3.2 说明性文件

- **资产文件是真实来源**：几何和像素以 `.bbmodel`、实际导出与 PNG 为准。报告与文件冲突时重新检查实际文件，不能修改报告数字来掩盖差异。
- **validation.json 是唯一验证摘要**：人工元数据（定名出处、来源、贡献者）只维护一次；计数、图片规格和内容摘要由共用工具提取；原生包围盒及实际验收证据在此登记。字段、命令与工具边界见 [ASSET_VALIDATION.md](ASSET_VALIDATION.md)。
- **README.md 只维护说明**：来历、设计意图、尺寸选择依据、识别特征、使用限制、本轮范围和版本差异；首屏链接 validation，不再手填实测计数、包围盒或重复一套通过清单。原作裁切等独立证据用链接引用。
- **structure_audit.json 按需保留**：只记录有价值的详细异常或原始审计证据，不再维护完整规格、重复总状态；无异常不强制新增。其历史报告不作为当前验收状态来源。
- **派生摘要不得手工分叉**：README 若显示规格，使用工具输出并标明来源；Discussion 和发布报告使用同一提交的记录链接或工具生成条目。无需为每件资产新增另一份长期 manifest。

### 3.3 `reference/`

放原作裁切、调色板、资产特有参数和必要证据。通用校验工具集中在 `tools/asset_delivery.py`；已具备原生截图时，不为核对预览另写一套渲染器。共用工具的源码及用法链接即可，不复制进每件资产。

**自建脚本必须可复现**：能在仓库根以相对路径重跑，不依赖作者本机私有路径。确需自建渲染时，共用实现放 `tools/`，资产在 `reference/` 保存调用参数；资产专用实现可放 reference。不得要求每个资产再造或复制相同工具。

允许的例外：一次性探索脚本、需要交互式环境（如 Blockbench 内 MCP 会话）才能运行的片段，可以不入库。此时 README 必须写明**该脚本的用途**以及**为什么无法在仓库内复现**；如果这个脚本正是预览的产出工具，还要写清预览的实际生成方式（例如"斜视图由自建光线步进渲染器生成，脚本未入库，故仓库内不可重现"），不要让读者误以为预览来自 Blockbench 内置截图。

## 4. 建模

**本节不设规范。** 建模手法、坐标取值、尺寸换算、几何与贴图细节由作者自行把控，可参考各自的建模笔记或外部资料。

交付约定只要求两件事，其余不做评价：

- 导出的 `.geo.json` 必须与 `.bbmodel` 一致（重出即可复现，见第 3.1 节）。
- 预览必须与当前几何一致（见第 6 节自查清单）。

原作者把资产交上来之后，评审只看交付是否合规，不改写作者的建模选择（见第 9 节）。

## 5. 运行时整合（升入正式资产后）

集成者负责，美术作者不直接改代码资源。

| 内容 | 目标位置 |
| --- | --- |
| 几何 | `src/main/resources/assets/barotrauma/geo/` 下的 `block/` 或 `entity/`，文件 `<标识>.geo.json` |
| 贴图 | `src/main/resources/assets/barotrauma/textures/` 下的 `block/`、`entity/` 或 `item/`，文件 `<标识>.png` |
| 动画 | `src/main/resources/assets/barotrauma/animations/` 下的 `block/` 或 `entity/`，文件 `<标识>.animation.json` |
| 物品图标 | `src/main/resources/assets/barotrauma/textures/item/<标识>.png` |

- 方块类资产还需 blockstate、block model、loot table、lang（中英）同步，命名与注册 id 完全一致，详见 `.mex/context/conventions.md`。
- GeckoLib 静态道具只需 geo + 贴图；有动画的资产补 animation 并在注册处声明。
- 整合后必须验证：渲染正确、UV 不串、轴心正确、暗环境下可读。

## 6. 验证

提交前自查（作者自证，写进 `validation.json`）：

- [ ] 四件套齐备且命名合规
- [ ] `geo.json` 能被解析，identifier 正确
- [ ] 实测规格与实际文件一致，唯一记录在 validation；原生包围盒有对应验收证据
- [ ] 贴图尺寸为 2 的幂，透明像素真透明
- [ ] 四向预览与当前几何一致（**几何改过就必须重出预览**）
- [ ] 无未使用的 cube / 孤立骨骼警告，或已解释

### 6.1 验收复用与上下文读取

- 新资产及下次修改的资产采用 validation schema 2（见 [记录格式与命令](ASSET_VALIDATION.md)）。`status` 每次依据实际内容计算；旧的 `complete`、相同 cube 数或文件日期都不能证明当前验收有效。
- 几何、贴图、预览分别记录内容摘要；验收包含依赖摘要、操作者、时间、工具版本和说明。相关内容变化显示 `stale`，未检查显示 `unverified`，禁止刷新时自动填通过。
- 几何/UV/分组/导出变化后重做相关导出和预览验收；仅重绘贴图时可复用几何验收，但须复核贴图与预览；仅修改预览时只复核预览；仅改说明文字时保留未受影响的验收。实际文件已变化而摘要未更新时，status 仍必须识别失效。
- 发布先运行共用工具的短 status。只有定位问题、修改相关规则或确认具体验收时，才展开对应字段、详细审计或文件。不得默认把整份 bbmodel、内嵌图片、所有历史报告及其他资产文档读入上下文。
- 历史资产不批量整改；下次修改时显式备份旧记录、迁移人工元数据并按实际证据验收，旧成功标记不自动转成新版通过。

集成后验证（集成者）：

- [ ] 游戏内可渲染，无缺贴图/紫黑面
- [ ] 尺寸与碰撞/占位相符
- [ ] 动画（若有）播放正常

## 7. 推送纪律

- **纯美术资产默认直推上游 `main`，不创建 PR、不等待 CodeRabbit 或 PR 门禁。** 维护者于 2026-11-15 确认此方式；用户明确要求发布指定资产，即授权该资产的提交与普通直推，无需再问是否直推。制作、预览或评估请求本身不包含发布授权。
- **范围**：仅限 `art/models/<标识>_<日期>/` 中的工程、导出、贴图、动画、预览、README、验证记录和配套 `reference/`；此发布分流适用于所有模型格式。涉及 `src/`、共享 `tools/`、发布规则或 CI 配置的改动另走任务分支 + PR，不与资产混提。
- **顺序**：确认资产与路径 → 完成交付自查 → 基于最新 `origin/main` 准备仅含本资产的提交 → 普通推送到上游 `main` → 确认远端 commit 与文件 → 登记 Discussion #39。入库后仍先进入「待评选」，直推不等于评选通过或运行时接入完成。
- 可使用基于已 fetch 的 `origin/main` 的独立 worktree，不要求拉取其他工作目录的本地 `main`；实际 pull 仍需单独授权。不强推；远端前进时重新 fetch 并保留远端变更后再推。没有上游写权限时报告并交维护者处理，不自动改为 PR。
- **纯资产记账**由本资产 README、`validation.json` 与 Discussion 登记承担，不为每次资产发布重复更新全局 ROUTER 或申请 `mex-skip`。共享约定、工具或项目能力发生变化时，仍按通用发布流程更新 MEX 文档。
- 一次资产发布只包含一个资产（或一组同批资产），不与代码改动混提。
- 推送内容：`art/models/<标识>_<日期>/` 全量（含 `reference/`）。**不含 `.work/`、`_archive/`**。
- 发布报告只写上游 commit、验证记录链接、登记链接和未完成事项；展示规格时从记录生成，不另维护手填数字。不得以直推跳过交付验收。

## 8. 登记与评选（Discussion #39）

三个分类，顺序固定，**章节标题与分类说明不得改写**。

| 分类 | 含义 | 条目要求 |
| --- | --- | --- |
| ✅ 正式资产 | 已入库 `main` 且定案 | 只放定位链接（工程/变体/动画/geo/贴图/预览），**不内嵌预览图** |
| 🔍 待评选资产 | 同一资产多候选并列 | 每候选一条任务列表项 + commit + 资产/验证记录/预览链接 + 从记录生成的制作来源；不再手抄几何规格。AI 参与时复选框后加 `🤖`；允许内嵌预览图 |
| 📌 待制作 / 待推送 | 需求池 | 三列表格（资产 / 类型 / 状态）；**不写本地路径** |

### 8.1 流转

1. **推送完成** → 从「待制作/推送」移除 → 用共用工具生成「待评选」候选，含同一提交的定位/验证/预览链接、来源与 commit。工具只生成文本，不代替远端核实或发布授权。
2. **评选通过** → 移入「正式资产」，去掉任务列表项，改为资产小节。
3. **落选** → 移入 `art/models/_archive/`，从讨论移除。

### 8.2 编辑纪律

- **只修改自己推送资产对应的条目**。章节标题、分类说明、命名规范、约定说明等文档性文字，非维护者不得改写。
- 新增需求用评论提出，由维护者定期合并进表格。

### 8.3 预览图缓存

GitHub 用 Camo 代理缓存外链图片，**同一 URL 的内容更新后页面仍显示旧图**。

- 内嵌预览的 URL 必须带版本参数：`?v=<数字>`（如 `?v=20261110`）。
- 该资产的图片每次更新后**递增该参数**。
- 共用工具默认生成 commit 固定的预览文件链接，不内嵌浮动图片；采用这种链接时无需额外维护版本参数。
- 「正式资产」只有链接，无此问题。

### 8.4 篇幅上限

- 「🔍 待评选」每个候选的说明块（`>` 引用）合计不超过 **400 字**（不含 URL），最多 3 段。
- 说明只保留评选所需信息：制作来源与分工、与上一版的关键差异、动画/已知问题、验证结论一句话。详细过程、逐项检查与复现步骤留在 `README.md` / `validation.json`，用链接指向，不复制到登记处。
- 「✅ 正式资产」每条只放定位链接，不写说明块。
- 超限条目在下次修改该条目时压缩；存量不单独追溯整改。

## 9. 退回条件（交付合规）

评审只判定**交付是否合规**，不评价建模手法与美术水平。出现下列任一情况退回：

- 四件套不全、命名不合规、目录结构不符第 2 节。
- `.geo.json` 无法解析，或 identifier 与 `<标识>` 不一致。
- 贴图不是 2 的幂，或透明区域实心。
- 预览与当前几何不一致（几何改过却没重出）。
- `.bbmodel` 重新打开后与本轮交付的几何不符，或依赖本机私有路径。
- 混入代码或 `src/main/resources` 改动（第 7 节）。

美术判断（像不像、比例好不好、细节够不够）不在本约定的退回范围内 —— 由维护者在 Discussion #39 评选时按作者标准决定（第 8 节）。
